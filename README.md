## 1. サービス概要

- このサービスはどんなサービスか  
  料理で非日常を味わいたい人が、「コストコの塊肉で、何か海外料理」のような曖昧な一言を伝えるだけで、海外の人が実際に食べているレシピを日本語で提案してもらえるWebサービスです。  
  料理名や国名を知らなくても大丈夫です。なんとなくのイメージ（雰囲気）を、具体的なレシピに変えます。

- 誰の、どんな課題を、どう解決するか
  - 誰の：家族ぐるみの集まりで、「いつもと違う料理」を振る舞いたい30代
  - どんな課題：海外料理に詳しくなく、検索に使う言葉（国名や料理名）がないため、何を調べればいいか分からず、始める前に諦めてしまう
  - どう解決するか：雰囲気を伝えるだけで、LLMが検索条件に変換し、海外の実在レシピを探して日本語で表示する。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- コストコで、憧れの大きな肉のかたまりを眺めていた。「これで何か海外の料理を作れないかな」と思ったが、どこの国の何という料理を調べればよいのか分からなかった。
- 「海外料理 レシピ 肉 ガッツリ」のように検索してみたが、イメージに近いレシピはあまり出てこなかった。数も思ったより少なかった。いろいろ探すのが面倒になり諦めた。
- そのとき、「もっと気軽に、抽象的な言葉で検索して、具体的な海外料理のレシピを提案してくれたらいいのに」と思った。

---

### 2-2. なぜそれが「気になった」のか

私は今まで、プログラミングやデジタルとは無縁の人生だった。ところがLLMが登場して、アプリを作るようになった。これを革新的だと感じた。

それまでは、「気になること」が抽象的なままだと、具体的な方法に落とし込むまでに、かなりの労力がかかった。何を調べればよいのか、どんな手順になるのかというイメージをつけるのが、いちばん大変だった。ところが、LLMに自然言語で抽象的な思いを壁打ちすることで、具体的な方法論まで落とし込めることが分かった。

「やってみたい気持ちはあるが、何から始めればいいのか、何を調べればいいのかも分からない」。方法を具体的に見つけるのに時間がかかって、頓挫してしまう。そうしたことに、LLMはかなり有効だと感じていた。その仕組みを活かせば、海外料理でも同じことができると思った。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

海外の料理を作ってみようと思っても、日本語で検索すると、イメージに近いレシピがあまり出てこない。そもそも何と調べればいいのかも分からない。


---

### 3-2. 本当に解決したい課題は何か

- なぜ困る？ → 海外の料理をあまり知らないので、調べるための言葉（国名や料理名）を持っていないから。
- なぜ言葉を持っていない？ → 普段、海外の食文化に触れる機会が少なく、知らないものは思い浮かばないから。
- なぜそれが困る？ → 知らないものは検索できないので、「やってみたい」という気持ちがあっても、最初の一歩で諦めてしまうから。

→ 本当に解決したい課題：やってみたい気持ちはあるのに、何から調べればいいか分からず、始める前に諦めてしまうこと。

「この人のことだ」と言える1人：  
家族ぐるみの付き合いがあり、週末に家族同士で集まる30代。バーベキューなどをして過ごすことが多いが、「いつもと違う料理を振る舞ってみたい」と思っている。コストコなどで大きな肉を見ては、「これで何か変わったものを作れないかな〜」と思っている。ただ、海外の料理は詳しくなく、何を調べればいいのか分からないので、結局いつもの料理になる。

年齢設定：
  - 年齢：30代
  - 理由：家族ができて、家族ぐるみの付き合いが増える年代。マイホームを持ち始める人も多く、友達やその家族を家に呼んで振る舞う機会が出てくるから。

生活・状況設定：
  - 生活・状況：家族ぐるみの付き合いで、週末に家族同士で集まる。
  - 理由：いつもと違う料理で喜んでもらいたいが、何を作ればいいか分からない。コストコでよく見る憧れの塊肉を焼くだけではなく別の形で使いたい。アプリでは、ノリを伝えるだけで、候補の海外料理が分かる。

環境設定：

## 7. このアプリで実現すること

### MVPで作る機能

- 会員登録・ログイン（ニックネーム、メールアドレス、パスワード）
- 気分の入力：「コストコの塊肉で何か海外料理」のような一言を入力する
- 検索条件の確認：LLMが解釈した内容を日本語の一文で表示し、「このまま探す」か「言い直す」を選べる
- レシピの検索結果の表示：海外の実在レシピを、画像・材料・手順つきで、LLMで日本語に翻訳して表示する
- 材料の置き換え：日本で手に入りにくい材料を、よくある材料に置き換えたレシピを見られる
- エラー時の案内：該当なしや、利用上限に達したときのメッセージを表示する

### 本リリースで作る機能

- アプリ内での投稿：作った料理の写真と評価を、レシピと紐づけて投稿する
- 自分の記録：作った料理を見返せる
- 他の人の投稿を見る（登録不要）
- 他の人の投稿から、そのレシピを検索することができる
- Instagramへの共有ボタン
- 検索回数の上限：1人あたりの1日の検索回数を制限する

## 8. このアプリの懸念点とその対策

### 懸念点①　気分を検索条件に置き換えたとき、雰囲気を正しく表せるか分からない

- 何が問題になりそうか：Spoonacularの検索は、気分の言葉を理解しない。そのため、気分を別の条件(カロリー、人数など)に置き換えて探すが、その置き換えが、ユーザーの感じる雰囲気と合っているとは限らない。

- なぜそう思うか：「がっつり」をカロリーの下限、「パーティ」を作れる人数に置き換えて検証したが、数字が気分の強さに合っているかは、まだ十分に確かめられていない。

- そのために考えている対策：LLMが解釈した内容を日本語の一文で見せ、ユーザーが言い直せるようにする。気分の種類ごとにテストを行い、置き換えの数字を見直す。

### 懸念点②　無料の枠では、利用が増えると足りなくなる

- 何が問題になりそうか：
  Spoonacularの無料プランは1日50ポイントまでで、使う人が増えると検索できなくなる。LLMの利用にも費用がかかる。

- なぜそう思うか：
  - 実測では、3件・材料・手順つきの検索1回で約1.25ポイント。カロリーなどの栄養条件を使うと、さらに約1ポイント増える。
  - このため、1日に検索できる回数は、栄養条件なしで約40回、ありで約22回ほど。
  - 検索のたびにLLMも1回呼ぶ。翻訳と置き換えを加えると、1回の検索あたりのLLMの呼び出しが増える。

- そのために考えている対策：
  - MVPでは、使う人が少ない前提で、検索の回数制限や有料プランは入れない。登録したユーザーだけが検索できるようにし、検索の前に条件を確認する画面を挟んで、無駄な検索を減らす。枠が尽きたときは、メッセージで案内する。
  - 本リリースでは、1人あたりの1日の検索回数に上限を設ける。
  - 利用が増えて足りなくなった場合は、有料プランへの切り替えを検討する。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- フレームワーク：Ruby on Rails 8.1.4
- DB：PostgreSQL（Neon）
- デプロイ先：Render
- 画像保存：検討中（本リリースで画像投稿を作るときに決める。候補：AWS S3など）
- メール送信：MVPでは送らない（本リリースで検討）
- LLM：検討中（複数のLLMを試して、費用・出力の安定さ・日本語の理解で比較して決める）
- 使用予定ライブラリ：
  - Devise（認証。MVPでは登録・ログインに必要な機能だけを使う）
  - Faraday（Spoonacular APIとの通信）
  - Bootstrap（CSS）
  - RSpec（テスト）

---

### 10-2. 技術選定の比較検討

| 項目 | 候補 | 採用/不採用 | 理由 |
| --- | --- | --- | --- |
| CSS | Bootstrap | 採用 | これまでの課題で使ってきた。部品が揃っていて、中心の機能（LLM連携）に集中できる |
| | Tailwind CSS | 不採用 | 自由度は高いが、デザインを自分で決める量が増える。今のCSSの理解では時間がかかると判断した |
| 認証 | Devise | 採用 | 認証の自作やhas_secure_passwordは経験した。今回は実績のあるgemを学びたい。使うのは必要な機能だけに絞る |
| 検索条件の作り方 | LLMで気分を条件に変換 | 採用 | 抽象的な雰囲気を具体化する中心の仕組みだから |
| | APIのフィルター使用 | 不採用 | 具体的にイメージを持っていないとユーザーはレシピを検索できないから |
| LLM | Claudeなど | 検討中 | 複数のLLMを試して、費用・出力の安定さ・日本語の理解で比較して決める |
| 翻訳 | LLM | 検討中 | 口調を調整でき、材料の置き換えも同時にできる可能性がある。一方、分量や単位を言い換えるリスクがある |
| | DeepL | 検討中 | 原文に忠実だが、訳が堅くなりやすい。置き換えには別にLLMが必要になる。実際のレシピで比べて決める |

| | MySQL | 不採用 | このアプリの規模では、速さや機能の差は出ない。DBの置き場所を別に探す必要があり、新しく学ぶことが増えるため |

| テスト | RSpec | 採用 | カリキュラムで使ってきた。使い方の理解を深めたい |

- 今回チャレンジしたい点：LLM（Claude API）と外部API（Spoonacular）を組み合わせて、気分を検索条件に変換する仕組みを作ること

### 10-3. キャッチアップ不足の懸念

- カリキュラムで使ったことがあるが、理解が浅いもの：
  Devise、RSpec、Bootstrap、Docker、Renderへの公開。今回の実装で理解を深めたい。

- 自力でのキャッチアップが必要なもの：
  - Claude API（公式のRuby用ライブラリ）の呼び出し
  - Spoonacular APIの使い方
  - LLMのプロンプトの作り方と出力のチェック

- 懸念点と対策：
  1. 完成までのハードルが高い
     このアプリの中心は、「雰囲気を伝えると筋のいいレシピが探せる」仕組みで、これが成り立つかどうかが一番不確か。早く試せるように実装して、試行錯誤をしたい。
  2. Issueの見積もりが難しい
     Railsの中でLLMやAPIを実装したことが少ないため、理解までにどれくらいの時間がかかるか分からない。

- Reactは、MVPの実装を終えたあと、組み込むかどうかを検討する。
